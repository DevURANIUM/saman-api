# جریان ورود و نشست سامان

نسخهٔ 0.3.0 جریان کاربردی ورود را بین CLI، HTTP و صفحهٔ وب مشترک می‌کند. پروتکل بانک، رمزگذاری و قالب درخواست انتقال تغییر نکرده‌اند.

## CLI

```sh
node cli.js login
```

تمام پیام‌ها و ورودی‌های برنامه انگلیسی‌اند: Username، Password و SMS code. نام کاربری، رمز مخفی و سپس در صورت نیاز کد پیامک پرسیده می‌شوند. ارسال پیامک خودکار است. پس از تأیید، همان نشست ذخیره و با بانک بررسی می‌شود. اگر هنگام واردکردن کد از برنامه خارج شدید، اجرای مجدد `login` بدون آرگومان همان مرحله را ادامه می‌دهد و پیامک دیگری نمی‌فرستد. برای ورود به حساب دیگر، نام کاربری را به فرمان بدهید. در پرسش کد، نوشتن resend همان‌جا کد جدید درخواست می‌کند.

آرگومان‌های `[username] [password]` هم پشتیبانی می‌شوند؛ برای استفادهٔ معمول، رمز را در پرسش مخفی وارد کنید. `otp-request` برای ارسال مجدد و `otp` برای سازگاری با اسکریپت‌های قبلی باقی مانده‌اند.

## صفحهٔ وب

بعد از اجرای سرور، `/login` یا `/auth/ui` را روی آدرس همان سرویس باز کنید؛ پیش‌فرض `http://127.0.0.1:8089/login` است. کلید API سرویس و اطلاعات ورود را بدهید، سپس کد را در مرحلهٔ دوم وارد کنید. کلید API در حافظهٔ صفحه نگهداری می‌شود و رمز پس از ارسال از فیلد پاک می‌شود. «ادامهٔ نشست قبلی» می‌تواند مرحلهٔ پیامک نیمه‌تمام را ادامه دهد. این صفحه روی سایت عمومی مستندات، اتصال بانکی ایجاد نمی‌کند.

## HTTP

1. `POST /v1/auth/login` با `username` و `password`.
2. اگر `otpRequired=true` و `otpSent=true` بود، کد پیامک را در رابط مصرف‌کننده بگیرید؛ ارسال پیامک دیگری لازم نیست.
3. `POST /v1/auth/otp` با `{ "code": "123456" }` را بفرستید. کد مثال ساختگی است.
4. `bankVerified=true` همراه `loggedIn=true` ورود کامل را مشخص می‌کند.

`ok` موفقیت مرحلهٔ ورود را نشان می‌دهد؛ در مرحلهٔ نیازمند کد هم می‌تواند true باشد. `nextAction` یکی از `verify_otp`، `otp_request`، `login`، `change_password_in_bank_app` یا null است. `otpError` خطای ارسال پیامک را شرح می‌دهد؛ نشست اولیه حفظ می‌شود. HTTP به‌جای پرسش تعاملی، وضعیت مرحله را به مصرف‌کننده برمی‌گرداند.

برای حفظ جریان قدیمی، در login مقدار `requestOtp:false` بفرستید؛ بعد `/auth/otp/request` را جدا فراخوانی کنید. مسیرهای `/login` و `/otp` و تمام مسیرهای قبلی API هنوز کار می‌کنند. `GET /login` صفحهٔ HTML است و `POST /login` همچنان API ورود است.

## استفاده و تمدید نشست

با تنظیم `SAMAN_USER` و `SAMAN_PASS` در محیط فرایند، نشست مفقود یا منقضی پیش از درخواست داده تمدید می‌شود. یک درخواست خواندنی پس از 401 بانک حداکثر یک‌بار احراز هویت و تکرار می‌شود؛ خطای شبکه چنین رفتاری ندارد. CLI خواندنی اگر به کد دستگاه نیاز داشته باشد همان‌جا آن را می‌پرسد. HTTP در این وضعیت 403 همراه `auth` و `nextAction` می‌دهد و درخواست داده را اجرا نمی‌کند. عملیات انتقال و نوشتن پس از خطا تکرار نمی‌شوند؛ پیش از انتقال CLI ورود را کامل کنید.

رمز ورود در فایل نشست ذخیره نمی‌شود. بدون این متغیرها، ورود مجدد را با `login` یا `/auth/session/ensure` و مشخصات بدنه انجام دهید. نشست قدیمی یا واردشده از HAR که هویت ورود آن مشخص نیست، باید ابتدا با login صریح به حساب متصل شود؛ تمدید خودکار حساب را عوض نمی‌کند. برای خواندن وضعیت محلی `status` و برای بررسی بانکی `check-session` باقی مانده‌اند. `ensure-session` و `check-session --renew` ورود نیمه‌تمام را نیز در CLI ادامه می‌دهند.

## سازگاری و بازگردانی

پیش از تغییر، بکاپ کامل خارج پوشهٔ پروژه تهیه و وجود کد و فایل نشست در آرشیو بررسی شد. اگر لازم بود بازگردانی انجام شود، سرویس باید متوقف و کد نسخهٔ قبلی از آرشیو جایگزین شود. بازگرداندن دادهٔ نشست قدیمی الزامی نیست؛ نشست فعلی را حفظ کنید مگر اینکه بازگردانی آن را هم بخواهید. فایل‌های بکاپ و نشست نباید منتشر شوند.

تست‌های تغییر از بانک شبیه‌سازی‌شده استفاده می‌کنند؛ ورود و انتقال واقعی توسط تست‌ها اجرا نمی‌شود.
